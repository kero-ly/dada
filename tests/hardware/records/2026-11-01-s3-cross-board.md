## 排查过程中我犯的两次误判

这段值得留着，因为两次都是**测量错误**，不是真 bug。

### 误判一：把"分区表偏移错位"当成 bootloader 问题

第一次全片烧录后画面不出来、串口静默，我判断"我们的 bootloader 不兼容"。

真实原因：PlatformIO 当时没有读 `partitions.csv`，把 app 烧到自己的默认偏移 `0x10000`，而分区表声称 app 在 `0x20000`。**固件和分区表错位，所以不启动。**

修法是显式声明 `board_build.partitions = partitions.csv`。这一步做完后，bootloader 其实就已经正常了——但我当时没意识到。

### 误判二：把"app 不打印"当成"app 崩溃"

加完分区表后串口仍然没有输出，我据此认为 bootloader 还是不行，绕道改用"只烧 app + 原厂 bootloader"。

真实原因：串口一直正常。`pet` 只在启动时打印两行，而每次读取都在启动之后，所以永远读到 0 字节。**没有心跳日志，就无法区分"应用死了"和"应用活着但不说话"。**

修法是让应用定期打印心跳：

```
pet: alive 10s breath=24 off=(1,0) heap=8680208
```

加上心跳后，`pio run -t upload` 全片烧录直接工作。

## 教训

1. **没有心跳日志时，"没有输出"无法区分死亡和沉默。** 任何长期运行的应用都应该定期报告自己还活着。
2. **串口读不到启动日志时，先怀疑读取时机，再怀疑固件。** USB 没有缓冲，复位瞬间的数据会丢；正确做法是让应用主动周期性输出。
3. **一次只改一个变量。** 我在分区表还没验证时就改了 console 配置，结果把板子搞进 boot loop，多花一小时恢复。

## 接线（ST7789 模块 → 通用排针）

| 屏 | 引脚 | 位置 |
| --- | --- | --- |
| VCC | 3V3 | 右列第 1 |
| GND | GND | 右列第 2 |
| DIN | GPIO9 | 右列第 6 |
| CLK | GPIO4 | 左列第 6 |
| CS | GPIO3 | 左列第 5 |
| DC | GPIO7 | 左列第 9 |
| RST | **GPIO6** | 左列第 8 |
| BL | GPIO5 | 左列第 7 |

板子自带的 18-pin LCD 座把 RST 接到 TCA9555 的 EXIO0，那个还没驱动，所以 RST 改接 GPIO6 拿硬复位。

## 未验证 / 未做

- 触摸：这块屏没有触控 IC，`input` 能力缺失。`pet` 因此改成 input 可选（只呼吸、不能摸头）。
- PSRAM 实际分配压力：只确认了堆大小，没有做分配稳定性测试。
- 音频、网络：不在本次范围。
- 桌宠的观感：见下文。

## 桌宠方向的结论

`pet` 能做到"角色在那儿、轻微起伏"，但**做不到"活"**。

原因是素材形态：单张平铺位图，所有变换（平移、垂直缩放都试过）只能作用于整幅画面，所以观感是"图片在动"。真正的桌宠需要分层素材（眼睛/头发/身体独立变换）或多帧精灵图。

这个方向暂停，等有合适素材再说。
